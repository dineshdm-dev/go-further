# Selecting an instrument

Read this only when the right next method is unclear. Choose by the obstacle, not by the prestige of a discipline. Name the input, operation, expected result, and failure check before applying a method.

| Obstacle | Candidate instrument | Evidence to seek | Important limit |
| --- | --- | --- | --- |
| A polished summary hides whether a claim holds | Reproduce one central result from underlying material | Agreement or a documented discrepancy under matched conditions | A reproduction supports only what it actually repeats |
| A decision changes with uncertain assumptions | Sensitivity analysis; explicit thresholds; value of additional information | Which plausible changes reverse the decision | Do not invent probabilities or personal preferences |
| A recurring failure is explained only by anecdotes | Reconstruct events and state transitions; examine denominators and competing explanations | A sequence and failure point supported by records | Incomplete records and selection effects can mislead; correlation is not causation |
| Someone can repeat an explanation but cannot use it | Prediction, counterexample, targeted diagnostic, transfer exercise | Correct performance on an unfamiliar case without hints | Success on rehearsed examples can conceal misunderstanding |
| A workflow looks usable on paper | Attempt its critical path in a clean setting; observe recovery | Successful completion and explicit friction or failure points | Agent execution is not a substitute for observing intended users |
| A spatial or dynamic relationship is hard to grasp | Interactive model, rendered scene, physical prototype, or small simulation | A task the representation helps the user perform | An attractive representation is not evidence of fidelity |
| A creative brief seems to have only obvious solutions | Test contrasting compositions, media, structures, or constraints | User preference against a clear brief; suitability for intended use | Creative quality need not have one objective score; preserve the user's taste |
| Repeated work depends on someone remembering every step | A bounded procedure or supported automation with explicit checkpoints | Correct operation on normal, missing-input, and failure cases | Successful local execution does not establish safe unattended operation |

## Borrow methods with a reason

Translate a problem into an operation before crossing fields. For example, a missed commitment may involve an unowned handoff; an undecided choice may involve missing preference information; an apparently slow process may involve waiting rather than execution time.

Treat these as hypotheses. Test the mapping against evidence. Drop the borrowed method when its assumptions fail or its result does not change the work.

Use ambitious targets to reveal alternative approaches. Check feasibility against physical, mathematical, financial, and operational constraints. Explain which constraint prevents a target when appropriate.

## Make verification affordable

Select the cheapest check that can meaningfully disprove the important claim. Escalate verification with consequence, irreversibility, and uncertainty. Use specialist review where the work requires expertise or access that the agent lacks.

Separate three questions:

1. Did the proposed mechanism run or follow logically?
2. Does it accomplish the user's intended task under the tested conditions?
3. What evidence is still needed before broader use?
